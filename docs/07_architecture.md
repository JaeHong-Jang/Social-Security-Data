# 아키텍처 v0.1

[기초설계](superpowers/specs/2026-11-17-ordinance-impact-design.md)와 [도메인 계약](05_domain-model.md)을 구현하기 위한 설계 초안이다. 아래 모듈·API는 아직 구현하지 않았다.

## 1. 기술 선택과 배치

기존 저장소의 FastAPI·Pydantic·React·TypeScript·Vite·Ollama 경험을 활용한다. 새 구현은 향후 prototype/ordinance_impact/에 분리하고 기존 이음등 API·가구 모델·화면은 수정하지 않는다.

| 요소 | MVP 결정 | 이유·제약 |
|---|---|---|
| 서버 | Python + FastAPI/Pydantic | 입력·출력 스키마와 상태 전이 검증 |
| 저장 | 표준 sqlite3 + 파일 스냅샷 | 작은 데이터에서 관계·버전·감사를 명시, 그래프 DB 불필요 |
| 수집 | 표준 HTTP/XML 도구로 고정 출처 어댑터 | 새 의존성 도입 전 기존 도구로 필요한 범위 검증 |
| AI | Ollama 어댑터, 모델·프롬프트 버전 설정 | 기존 로컬 환경 활용, 적합한 모델은 평가 후 결정 |
| 웹 | React/TypeScript/Vite | 검토·비교 화면을 별도 앱으로 구성 |
| 작업 | 단일 서버의 제한된 로컬 작업 실행기 | 작업 상태·입력 묶음을 DB에 저장, 시작 시 미완료 작업 복구 |

로컬 단일 사용자 데모가 기본이다. 외부 네트워크 공개·멀티 인스턴스·조직 인증은 MVP 배치 범위가 아니다. 도입 때는 인증, 내구성 있는 작업 큐, 조직별 데이터 분리, 보존 정책을 별도 설계한다. 새 패키지가 반드시 필요하면 범위를 확인한 후 선택한다.

## 3. 데이터 흐름 뷰

1. **등록:** 지자체와 허용 출처, 사업, 안내자료 관리 책임을 등록한다. 후보 관계는 확인되기 전 승인의 근거가 되지 않는다.
2. **수집:** 응답 상태·유형·크기·관할·식별자를 검사한다. 원문 바이트를 해시하고 추출 텍스트·파서 버전·관측 시각을 저장한다.
3. **변경 발견:** 법규 내부 ID와 외부 연혁 정보를 이용해 전후 버전을 선택한다. 동일 해시는 재수집, 이전 원문 미확보는 근거 부족으로 기록한다.
4. **고정 입력:** 전후 법규·부칙, 사업 상세, 연결 확인 버전, 등록 안내자료 전체 목록과 스냅샷, 판단 기준일을 analysis manifest로 고정한다.
5. **비교:** 조문 번호·제목·문장 이동을 함께 확인한다. 명시된 조건의 값·단위·경계와 적용 조건을 분리한다.
6. **영향 확인:** 확인된 연결의 안내자료를 모두 검사하고 자료별 성공·보류·실패를 기록한다. 누락된 자료는 전체 진행률에 남긴다.
7. **검토:** 검토자는 원문·부칙·현재 안내를 비교한다. 근거 보충·적용 판단 변경은 새 분석 회차를 만든다.
8. **승인:** 현재 회차·결정 버전·원문 해시·재확인 유효 기간·승인 불변식을 하나의 트랜잭션으로 검사하고 감사 사건을 추가한다.
9. **수정 확인:** 외부 변경은 사람이 수행한다. APPROVED 이후 수집된 안내 스냅샷은 verification_for_approval로 기존 승인에 연결하고 원래 입력과 분리한다. 담당자가 예상 수정만 반영되었고 다른 근거가 그대로임을 확인하면 기존 회차를 VERIFIED로 전이한다. 미반영·일부 반영은 실패 이력만 추가하고, 범위 밖의 실질 변경·다른 근거 변경은 새 분석 회차를 만든다. 자동 스캔 결과에도 같은 분류를 적용한다.

원문 파일은 임시 파일 작성→해시 검증→불변 저장 경로 확정 순서로 저장한다. DB에서는 완성된 파일만 참조하고 분석 결과·상태·감사는 트랜잭션으로 함께 기록한다. 고아 파일은 후속 정리 대상으로 남겨도 되지만 없는 원문에 대한 승인 기록은 만들 수 없다.

## 4. AI 실행 뷰

자유롭게 도구를 호출하는 에이전트보다 **단계가 정해진 처리 흐름**을 사용한다.

| 단계 | 입력 | AI 출력 | 일반 코드의 검사·제한 |
|---|---|---|---|
| 조문 대응 보조 | 같은 법규의 전후 조문 후보 | 대응 조문·이동 여부·근거 | 관할·버전·조문 존재, 인용 일치 |
| 조건 변화 추출 | 대응 조문·부칙 | 조건 유형, 전후 값, 단위·경계, 인용 | Pydantic, 원문 구간, 수치·단위 대응 |
| 영향 사유 제안 | 확인된 연결, 조건 변화, 안내 문단, 적용 판단 | 자료별 일치/불일치/미확인과 사유 | 모든 등록 자료 처리 여부, 판단 근거 검증 |
| 정정 초안 | 적용이 확인된 영향 항목과 원문 | 해당 구간 대체문·근거 참조 | 무근거 값, 누락 인용, 범위 밖 변경 차단 |

- 외부 문서는 프롬프트 지시와 분리된 데이터 영역으로 전달한다. 문서가 요청한 URL 접속·실행·키 공개를 수행하지 않는다.
- 모델에는 고정된 필요한 문단만 보내되, 부칙·참조 조건 누락을 탐지한다. 컨텍스트 크기를 넘으면 조문 단위로 나누고 원문 위치를 유지한다.
- MVP의 비교 대상은 확인된 연결의 **등록 자료 전체**다. 검색으로 찾지 못한 문서도 검사 목록에서 사라지지 않는다.
- 스키마/인용 실패는 제한된 재시도 **1회** 후 실패·보류로 남긴다. 초기 정책이며 모델별 평가 후 조정한다.
- 프롬프트 해시·모델 식별자/설정·입력 manifest·출력 검증 결과를 기록한다. 실행마다 동일 문장이 나온다고 보장하지 않는다.
- 모델 부재 시 원문·규칙 비교·수동 검토는 가능하다. AI 기능 실패 배지를 표시하고 가짜 출력으로 대체하지 않는다.
- 도메인 상태 전이와 승인 규칙은 모델 밖에서 강제한다. 분석 작업에는 승인 권한이 없다.

구조화 결과 필수 항목: condition_type, before/after(value, unit, operator), evidence_refs, applicability_status, unresolved_reasons. 값이 원문에 없으면 null과 이유를 쓰며 추정하지 않는다. 실제 JSON Schema는 구현 때 이 계약에서 정의한다.

실제 인증 API 수집은 아직 검증하지 않았다. 출처·이용 제한의 근거는 [조사 문서](../research/ordinance-impact-sources.md)에 분리한다. 외부 API 실패 시 과거 스냅샷으로 “현재 최신 검사 완료”라고 표시하지 않는다.

## 6. 보안·신뢰 경계 뷰

- 브라우저 입력, 공개 문서, AI 출력 모두 검증 대상이다. 서버의 상태 전이·출처 검사·인용 검사를 우회하지 못한다.
- 서버 수집은 등록한 호스트·경로만 허용한다. 내부/루프백/링크로컬 IP·비HTTP 계열·자격증명 포함 URL을 차단한다.
  리다이렉트와 DNS 해석 결과도 매번 검사한다. 모델 실행기의 로컬 Ollama 연결 설정과 문서 수집 URL은 별도 정책이다.
- 문서 fetch에는 API 인증키를 붙이지 않는다. 출처별 인증 정보는 해당 API 어댑터만 사용한다.
- 문서 크기·응답 시간·리다이렉트 수를 제한한다. HTML은 텍스트 추출 후 표시하고 원문 HTML 스크립트를 실행하지 않는다.
- 환경파일·키는 버전 관리하지 않고 요청 URL·예외·접속 로그에서도 제거한다.
- 공개 문서에 개인 연락처 등 불필요한 정보가 있으면 모델 입력에서 제외한다. 개인별 신청서·상담자료는 등록하지 않는다.
- 로컬 시연은 루프백 바인딩, 시연 역할 표시. 실제 인증·기관별 권한이 없는 상태로 외부에 공개하지 않는다.
- 외부 게시 API, 자동 승인 도구, 내부 행정망 접속 도구를 제공하지 않는다.

## 7. API 경계 초안

모든 경로의 접두사는 /api/ordinance-impact 이다. 아래 이름은 구현 전 계약 초안이다.

| 메서드·경로 | 역할·핵심 계약 |
|---|---|
| GET /sources, /sources/{id}/snapshots | 출처와 관측·버전·실패·최신성 조회 |
| POST /sources | 허용 출처 등록. 서버 URL 정책 검사 |
| POST /sources/{id}/fetch | 비동기 수집 요청, 202와 job_id |
| POST /scans | 등록 범위 스캔 요청, 기준일·출처 집합 고정 |
| GET /jobs/{id} | 상태, 전체/성공/실패/보류 건수와 재시도 가능 여부 |
| GET /amendments | 법규 버전쌍·공포/시행 정보·수집 범위 |
| GET /impacts, /impacts/{id} | 검토 목록·현재 회차·비교 근거·이력 |
| POST /service-legal-links/{id}/decisions | 업무 검토자의 관계 확인/거절, 근거·사유 필수 |
| POST /service-guidance-links/{id}/decisions | 사업–자료 연결 확인/거절 |
| POST /impacts/{id}/assessments | 적용 판단·추가 근거 기록 후 새 회차 생성 |
| POST /impacts/{id}/drafts | 지정 회차에서 초안 생성/새 버전 등록 |
| POST /impacts/{id}/decisions | 승인·수정 요청·검토 제외. 도메인 불변식 검사 |
| POST /impacts/{id}/verifications | 재수집 스냅샷과 검토 결과 기록 |

이미 등록된 객체를 변경하는 요청은 analysis_revision과 decision_version 또는 관계의 자체 version에 대한 If-Match가 필수다. 예: ETag "ic001:r3:d2". 누락은 428, 불일치는 412, 현재 상태에서 허용되지 않는 전이는 409, 형식 오류는 422로 응답한다.

입력 버전 확인과 결정 저장은 동일 트랜잭션이다. 작업 결과에도 시작 회차를 대조한다. 승인 연타·중복 수집 요청에는 idempotency key를 사용해 같은 결과를 재사용한다. 서로 다른 승인 초안이 같은 구간을 바꾸면 충돌을 표시한다. 검토 제외는 분석 회차를 반드시 참조하고 초안이 없는 READY 상태에서는 draft_version을 null로 허용한다. 외부 게시 엔드포인트는 없다.

## 8. 감사·재현 뷰

분석마다 다음 manifest를 보존한다.

- 원문/텍스트 스냅샷 ID와 해시, 전후 법규 ID, 수집 시각·기준일
- 사용한 사업·자료 연결의 버전과 확인 근거
- 파서·비교 규칙·프롬프트 버전, 모델 식별자와 실행 설정
- 인용·구조 검사 결과, 보류 사유, 처리한 자료 목록과 실패 목록
- 담당자 결정·초안 버전·수정 확인 스냅샷·감사 요청 ID

과거 검토는 당시 manifest와 근거로 다시 열어 본다. 새 수집이 과거 인용을 깨뜨리지 않는다. 전체 프롬프트·응답의 상세 저장은 접근 제한한 로컬 분석 산출물에 두고 일반 운영 로그에는 필요한 메타데이터만 기록한다. 키·개인정보는 어느 쪽에도 저장하지 않는다.

| 실패 | 표면화·처리 | 재시도/대안 |
|---|---|---|
| 인증·호출 한도·네트워크 오류 | SourceFetchFailed, 미검사/최신성 표시 | 제한된 지수 대기, 한도 오류는 자동 반복 중지, 수동 재시도 |
| 이전 버전·부칙·필수 별표 누락 | NEEDS_EVIDENCE, 누락 항목 표시 | 공식 원문 추가 등록. 전국 별표 제공 가정 금지 |
| 사업 법규 연결 불명확 | 후보 상태, 승인 차단 | 관할·명칭·사업 근거를 사람이 확인 |
| 모델 실패·무효 JSON·허위 인용 | 작업 DEGRADED/FAILED, 초안 승인 불가 | 규칙 기반 비교·수동 검토 |
| 중간 자료 수집 실패 | 완료된 결과와 미검사 목록 함께 표시 | 실패 자료만 재수집, 전체 성공 표시 금지 |
| 승인 전 입력 변경·승인 후 다른 근거 변경 | If-Match 충돌 또는 새 회차 | 변경 근거로 재검토, 이전 결정 보존. 예상 안내 수정은 별도 확인 증거 |
| 서버 재시작·작업 중단 | RUNNING 작업을 복구 대기로 표시 | 동일 manifest로 재개/재실행, 중복 결과 방지 |
| 수정 후 일부만 반영 | VerificationFailed, APPROVED 유지 | 누락 위치 제시 후 다시 확인 |
| 보관 공고와 현행 기준 차이 | 자료 대상 시기 확인 | 미적용 제외 또는 NEEDS_EVIDENCE, 일괄 정정 금지 |

## 10. 도입 전 남은 결정

MVP에서는 단일 로컬 작업·작은 자료 집합에 맞춘다. 인증 API 실제 응답, 연혁 ID의 안정성, 원문 사용조건, 모델 적합성, 기관 승인 권한·감사 보존 정책은 검증 전이다. 이 항목들이 해소되기 전에는 운영 배포 가능하다고 설명하지 않는다.
